Overview

Test Data Generator builds realistic fake data from a schema you define: add fields, pick a type for each, press download. Output is nested XML, JSON, or flat CSV. Everything runs in your browser — no server, no account, and no data leaves the page.

Quick start

  1. Add a field (or press Load example). Each card has the field name on top and the type picker below it.
  2. Click the type bar (the wide bar under the field name, with the ⌄). It opens onto every category with its count — click one to expand it, or just start typing to search across all of them at once.
  3. Watch the preview update as you edit (Ctrl/⌘+Enter refreshes on demand). Each card also shows a live sample value.
  4. Pick a format, set the row count, and Download.

Drag the dotted handle to reorder fields; the copy icon duplicates a field.

Nesting, attributes & repeats

Structure lives in the field name, using three pieces of syntax:

SyntaxMeaningXML output
address.citydots nest elements<address><city>…</city></address>
order.@id@ on the last part makes an XML attribute<order id="…">
friend[3]repeat exactly 3×three <friend> elements
item[2-5]repeat a random 2–5× per record2–5 <item> elements

Shared counts: sibling fields under the same repeating segment share one count per record, so the parts of each repeated element line up. These two fields always produce the same number of orders:

orders.order[1-3].sku
orders.order[1-3].qty

In JSON that becomes:

"orders": { "order": [
  { "sku": "978-1-56619-909-4", "qty": 2 },
  { "sku": "978-0-7645-7682-9", "qty": 7 }
] }

One repeating segment per field path. In CSV, nested names become the column header and repeated values are joined with |.

Linked entities (referential integrity)

When you need separate files that join by ID — Accounts and the Contacts that point at them — add an entity tab per record type. Each tab has its own fields, row count, and (for XML) element names.

Generation order is tab order, left to right, in one run. Parents generate first, then children pick from the values the parents actually produced — so every run, and every download, is internally consistent. Use the ‹ › arrows on the active tab to reorder, and rename a tab in place.

The Reference field

On the child, give the linking field the Reference type and pick the source entity and field:

Contacts · account_id
  Reference → from: Accounts · field: id
  • Default: each child picks a random parent value — a natural many-to-one (several Contacts per Account).
  • unique: each parent value is used at most once — a one-to-one link. If the child has more rows than the parent has values, the extra rows come out as #REF and the status bar warns you before you download.

A Reference may only point at a tab to its left (parents must exist first); anything else produces #REF with an explanation in the status bar. Formulas on the child can read the reference like any other field — e.g. field('account_id') + '-' + field('id') for a compound key. To carry several fields from the same parent (id and name together), see Cross-entity: id AND name from the same parent under Formula recipes.

Downloading

Download saves the active tab's file. Download all saves one .zip holding a file per entity (accounts.csv, contacts.csv, …) from a single generation run, so the IDs line up across files, plus the schema.json that produced them. One archive rather than a download per entity, because a click that starts several downloads in a row is what browsers interrupt with “wants to download multiple files”. With a seed set, the entire linked dataset is reproducible, and the archive is named for that seed.

The live preview samples parent values from each parent's first 500 rows to stay fast; downloads always generate full row counts.

Testing matching & dedup

To test a matching or deduplication engine you need records that are almost the same — a person entered twice with a typo, a different phone format, a missing value. The dups control in the toolbar does this per entity:

dups: [ off | light | medium | heavy ]   20 %   × 2

With dups on, the chosen percentage of records get 1 to ×N fuzzed duplicate variants. Rows are shuffled so duplicates are not adjacent, and a match_id column is added: an original and its variants share a value, a record with no duplicates has its own. That column is the ground truth — pairs that share a match_id should match; strip the column before feeding the file to your matcher, then score its output — the Score matcher dialog does that for you.

What each level does

LevelFields fuzzedKinds of damage
light1case changes and stray whitespace only — trivially matchable
medium1–2typos (transpose / drop / double a letter), email local-part fuzz, phone reformatting, date ±1 day, a wrong digit in a zip
heavy2–3everything above, plus double typos, blanked values, transposed month/day, numbers ±1
targetedyour choiceper-field similarity thresholds — see Targeted similarity below

Damage is chosen by field type, so a phone gets reformatted rather than misspelled and a date shifts by a day rather than gaining a letter.

Targeted similarity

The presets make records messy; the targeted level makes them exactly this hard to match. Choose dups: targeted and each field card gains a similarity control:

address   [ Jaro-Winkler ≈ ]  [ 0.90 ]
name      [ exact copy in variants ]

A variant's targeted field is fuzzed until its similarity to the original lands as close as possible to the threshold under the chosen algorithm — Jaro-Winkler or Levenshtein (normalized) — while every field left at exact copy is copied unchanged. That lets you generate pairs right at your matcher's threshold: a batch at 0.92 that should match and a batch at 0.80 that shouldn't.

Similarity is quantized — each character edit moves the score in steps, and a short value like TX can't land on an arbitrary number — so the engine gets as close as it can and the status bar reports the achieved average per field (e.g. address 0.897) as the preview refreshes. In testing, targets of 0.75–0.90 on realistic names and addresses land within ±0.03 essentially always.

What stays intact

  • UUID fields regenerate on each variant — a duplicate is a distinct system record with its own ID.
  • Row Number renumbers sequentially over the final (shuffled) output.
  • Reference, Boolean and Static Value fields are copied unchanged — a duplicate Contact still points at the same Account.
  • Formula (JS) fields are not re-evaluated on variants. A variant is a corrupted copy of a finished record: all field rules run once when the base record generates, and from there only the dups settings decide the corruption. A derived field (like a name-based email) keeps the value computed from the original spelling — which mirrors real duplicate data, where the old email survives the misspelled re-entry.

The row count is the number of base records; the output file is larger by the variants. With a seed set, the entire messy dataset — including which records got duplicates and how they were fuzzed — is reproducible.

Scoring a matcher against the ground truth

The match_id column is the answer key. Score matcher in the header compares what your matcher linked with what the key says should have been linked. The workflow:

  1. Turn dups on for the entity, set a seed, and Download.
  2. Hold back the match_id column (the dialog can also download it alone as an answer key), and run your matcher on everything else.
  3. Open Score matcher. Leave the ground truth on This entity + seed — the same seed regenerates the same rows, so nothing has to be uploaded — or paste the downloaded file if the schema has changed since.
  4. Paste the pairs the matcher linked, one id_a,id_b per line (or id_a,id_b,score, or JSON), and press Score.

What the numbers mean

Truth partitions the records into clusters (singletons plus groups of 2–5). The matcher produces its own partition. Both are turned into sets of record pairs so agreement is countable: a 3-record cluster is 3 pairs.

true pairs      every pair of records sharing a match_id
predicted pairs every pair the matcher linked
TP  in both       FP  predicted only (a false merge)       FN  true only (a missed match)

precision = TP / (TP + FP)      recall = TP / (TP + FN)      F1 = their harmonic mean

Three things the scorer does deliberately:

  • It never reports accuracy. With 100 records there are 4,950 possible pairs and maybe 40 true matches, so a matcher that links nothing scores 99.2% accuracy. Precision and recall only.
  • It closes the links under transitivity first. If the matcher emits A–B and B–C but not A–C, connected components are built from its links and pairs are re-enumerated within each component. Otherwise it is penalised for a pair it logically implied. Untick close under transitivity to score the raw links.
  • It scores blocking separately. A true pair whose two records land in different blocks can never be found, whatever the threshold. Pick a blocking key field in step 1 (or paste your candidate pairs) and the dialog reports pair completeness — the fraction of true pairs that survive blocking, which is your recall ceiling — alongside the reduction ratio, how much of the pair space blocking cut. The two trade off.

With scores: the three numbers that matter

If each pair carries a score, the dialog also sweeps the threshold from 0.5 to 1.0 and shows precision and recall at each cut. But pick thresholds by operational cost, not F1: in patient matching a false merge (two people's charts combined) is far worse than a false split. So production runs a high-precision auto-merge band and sends the middle band to a stewardship queue, and the report gives you the three numbers that describe that:

auto-merge  score ≥ 0.92   merged without a human      → auto-merge precision, auto-merge recall
review      0.78 – 0.92    stewardship queue           → queue size, how many true pairs it holds
below       score < 0.78     left alone                   → recall after a perfect review

Both band edges are editable. Recall after a perfect review is what you would reach if every queued pair were adjudicated correctly.

Reading the mistakes

Every false merge and missed match is listed by record id. Look them up in the generated file: a recall gap is usually a name problem (nicknames, married names), a date problem (transposed month and day), or a blocking problem (the block key was built from a field the dups fuzzed) — and the pairs tell you which.

The dialog also warns when ids in the matcher output are not in the truth set. They count as false merges, and they almost always mean a different id column was used on each side.

Nothing in the scorer is patient-specific: it scores a Providers entity, or any other, identically. The same scorer is exposed as POST /v1/score in the HTTP API, where the truth can be regenerated from the same (schemaId, count, seed) that produced the data, and it lives in scoring.js for use from Node.

Simulating a matcher

You do not need a matching engine to use the scorer. Switch step 2 of Score matcher from Paste pairs to Simulate a matcher and configure one here; it runs against the generated records and is scored the same way.

Rules and comparisons

The model is the one MDM products use, because it is the one people already think in:

a RULE  is a set of field comparisons, ALL of which must pass   (and)
a PAIR  is linked if ANY rule passes                            (or)

So a strict rule sits beside a loose one and a pair linked by either is linked. Each rule carries a confidence, and a pair's score is the highest confidence among the rules that passed it — which is what lets a strict rule auto-merge while a loose one only earns a place in the review queue.

ComparisonMatches when
is exactlythe two values are identical, character for character
matches ignoring case and punctuationO'Brien-Smith equals obrien smith
first N characters matcha shared prefix, after the same normalisation
sounds alike (Soundex)Smith equals Smyth; the classic surname coder
same words in any orderJohn Smith equals Smith, John
Jaro-Winkler at leastsimilarity reaches your threshold; favours a shared start
Levenshtein at leastnormalized edit distance reaches your threshold
Jaro-Winkler on sorted words at leastfuzzy and order-insensitive
numbers withinnumeric values differ by no more than your tolerance
dates withinparseable dates differ by no more than N days

Suggest rules reads the field names and proposes a starting set to edit. Nothing about it is clever; it exists so nobody faces an empty rule builder wondering what a rule looks like.

Blanks

By default a blank value fails its comparison: absence of evidence is not agreement. Tick blanks still agree and a blank is skipped instead, which is what you want when an optional field like a middle initial should not sink an otherwise convincing name match. A rule never passes on skipped comparisons alone — at least one comparison has to have actually been evaluated, or a record with every field blank would link to the entire file.

Blocking is derived, not configured

A rule containing an equality comparison — exact, first-N, Soundex, same-words — can only ever match records that agree on it, so those comparisons compose into a key and the rule is evaluated inside key groups instead of over every pair. That is blocking, arrived at for free. A rule built only of fuzzy comparisons has no such key and costs the full n²; the builder says so under the rule, and a run that would exceed the comparison budget is refused with an explanation rather than freezing the tab.

Reading the per-rule table

The report gains a row per rule: how many pairs it compared, how many it linked, how many of those were right, and how many were over-matches. That is how you find the single rule that is too loose without guessing. A pair several rules agree on is counted under each of them, so the columns overlap by design.

The whole loop lives on one page: design a schema, generate it with known duplicates, configure a matcher, and read how many records it over- and under-matched — then change one threshold and run it again.

Formulas (JS)

A Formula (JS) field is a JavaScript expression evaluated per record, after all other fields — so it can read them. Formulas run in field order, so a formula can also reference an earlier formula.

NameWhat it gives you
field('name')the value of another field (at the current repeat index, if repeated)
fields('name')the full array for a repeated field
ithe current repeat index (0-based) when the formula field itself repeats
rowthe whole record so far, keyed by field name
normalize(s)lowercase, strip everything but letters and digits
concat(a, b, …)join values into one string
pad(v, len, ch?)left-pad to a length, '0' by default
rand(min, max)random integer, inclusive — uses the seed

Any plain JavaScript works too: string methods, Math, ternaries, template literals. Formulas run in your own browser on data generated in the page — still, only paste expressions you trust.

Formula recipes

Most of these insert themselves: the Recipes button in the app (next to Add field) adds any of them as a pre-wired group of ordinary fields. Recipes that read other fields show a linking step first: each input gets a dropdown of your current fields (the auto-detected match preselected — works on imported schemas too) with a create option, so you decide exactly what links where. Everything inserted is a plain, editable field.

Copy these into a Formula (JS) field's expression box. They assume fields named first_name, last_name, etc. — change the names to match your schema.

Combining fields

// username: lenora.kuhlman
(field('first_name') + '.' + field('last_name')).toLowerCase()

// full name with a middle initial
field('first_name') + ' ' + field('middle')[0] + '. ' + field('last_name')

// normalize: lenorakuhlman (lowercase, letters and digits only)
normalize(field('first_name') + field('last_name'))

// email DERIVED from the name fields (use Formula, not the Email type):
(field('first_name') + '.' + field('last_name')).toLowerCase().replace(/[^a-z0-9.]/g,'') + '@acme-test.com'

// realistic variety: jdoe, jane.doe, jane_doe83 — seeded, reproducible
(()=>{
  const f = String(field('first_name')).toLowerCase().replace(/[^a-z]/g,'');
  const l = String(field('last_name')).toLowerCase().replace(/[^a-z]/g,'');
  const forms   = [f+'.'+l, f[0]+l, f+'_'+l+rand(1,99), l+'.'+f[0]];
  const domains = ['gmail.com','yahoo.com','outlook.com','acme-test.com'];
  return forms[rand(0,3)] + '@' + domains[rand(0,3)];
})()

Formulas are the dependency mechanism: they run after all other fields, and a formula may read an earlier formula — so username can derive from names and email from username, in that field order.

Consistent city / state / zip (and area code)

The built-in address types are independent random draws — the zip won't belong to the city, and the city won't be in the state (the underlying Faker library's cities are fictional, so no true mapping exists). The fix for any group of fields that must agree is one shared source field plus formulas that split it:

// geo — Custom List, values: City|ST|Zip|AreaCode
Springfield|IL|62701|217, Austin|TX|78701|512, Denver|CO|80202|303, Portland|OR|97201|503

// city / state / zip — three Formula (JS) fields
field('geo').split('|')[0]
field('geo').split('|')[1]
field('geo').split('|')[2]

Each record picks one entry, so every part stays consistent. The helper geo column does appear in the output — name it something downstream consumers can ignore.

Phone and fax tied to the city

Building on the geo quad above: the phone's area code comes from the record's own city, and the fax shares the phone's area code and exchange — the way office numbers actually look.

// phone — Formula (JS): area code from geo → (303) 735-1748
'(' + field('geo').split('|')[3] + ') ' + pad(rand(200,999),3) + '-' + pad(rand(0,9999),4)

// fax — Formula (JS): same area code and exchange, different line → (303) 735-5265
field('phone').slice(0,-4) + pad(rand(0,9999),4)

International addresses

Same shared-source pattern, one level up: the source entry carries the country's city, phone prefix and currency, while the postal code generates fresh per record in that country's format — UK PA3 1EV, Canada R8L 2X7, Japan 448-8524, Netherlands 5389 VH — which is what address-format validation actually tests.

United Kingdom|London|+44|GBP, Germany|Berlin|+49|EUR, Canada|Toronto|+1|CAD,
Australia|Sydney|+61|AUD, Japan|Tokyo|+81|JPY, France|Paris|+33|EUR,
Netherlands|Amsterdam|+31|EUR, Brazil|São Paulo|+55|BRL

Cross-entity: id AND name from the same parent

The trap: two separate Reference fields to the same entity pick independently — a contact would get one account's id and a different account's name. The fix is the same shared-source pattern across entities: give the parent a composite key, reference that, and split it on the child.

// on Accounts:  key — Formula (JS)
field('id') + '|' + field('name')

// on Contacts:  acct — Reference → Accounts.key, then two formulas:
field('acct').split('|')[0]                      // account_id
field('acct').split('|').slice(1).join('|')      // account_name (safe if the name has a |)

CRM-style record IDs

Every recipe below uses rand(), so a seed makes the IDs reproducible.

// Salesforce 15-char ID: 003AD8rgZcOitPJ
// key prefix picks the object: 001 Account · 003 Contact · 006 Opportunity · 00Q Lead · 500 Case
'003' + Array.from({length: 12}, () => 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789'[rand(0, 61)]).join('')

// Salesforce 18-char ID with a VALID checksum suffix: 006vgMWShS8P2LIAX0
// (the last 3 chars encode the casing of the first 15, like real SF IDs)
(() => {
  const chars = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789';
  let id = '006';                                    // 006 = Opportunity
  for (let k = 0; k < 12; k++) id += chars[rand(0, 61)];
  const map = 'ABCDEFGHIJKLMNOPQRSTUVWXYZ012345';    // real SF suffix alphabet
  let sfx = '';
  for (let c = 0; c < 3; c++) {                      // 3 chunks of 5 chars:
    let b = 0;                                       // bit per uppercase position
    for (let p = 0; p < 5; p++) if (id[c*5+p] >= 'A' && id[c*5+p] <= 'Z') b |= 1 << p;
    sfx += map[b];
  }
  return id + sfx;
})()

Country, city and postal code that agree

Each method is an independent draw, so geoEurope.country and geoEurope.city in two separate fields will not line up. When the values must agree on a row, use place — it returns one JSON object — and split it with formulas:

The same pattern works for intlJapan.place (adds name and street) and for intlAny.place, which changes country every row. Give the source field a name starting with _ if you would rather remember which column is scaffolding — it is still exported, so delete it if you do not want it in the output.

Writing your own module

Add methods by editing faker-ext.js in the repository — no build step, no rebundling of faker.iife.js. It loads before the app boots, and the type picker is built by walking the faker object, so anything you add simply appears.

FakerLib.faker.acme = {
  productCode: function () {
    // compose faker's own methods, never Math.random()
    return 'ACME-' + FakerLib.faker.string.alphanumeric(6).toUpperCase();
  },
  warehouse: function () {
    return FakerLib.faker.helpers.arrayElement(['DAL-1', 'ATL-2', 'PHX-3']);
  }
};

Testing locally: opening index.html straight from disk does not work — browsers block the page's script loads over file:// and nothing boots. Serve the folder instead (python3 -m http.server) and open localhost. The type count in the toolbar tells you whether your module was picked up.

Seeds & reproducibility

Leave seed empty for different data on every run. Set a seed and the same schema + seed produces byte-identical output, every time, on any machine — useful for repeatable test suites. The preview shows which seed was used, so you can pin a result you like.

    { "name": "Contacts", "rows": "100", "root": "contacts", "record": "contact",
      "fields": [
        { "name": "first_name", "type": "First Name", "opts": {} },
        { "name": "account_id", "type": "Reference",
          "opts": { "entity": "Accounts", "field": "id", "unique": "" } }
      ] }
  ]
}

Older single-entity schema files ({"root", "record", "fields": […]}) still import — they load as one entity.

# Schema JSON specification (v2)

This document fully specifies the import/export file format of **Test Data
Generator** (https://dnguye.github.io/Test-data-generator/). It is written so
that a person — or an AI given an XSD, sample XML, or a plain description —
can author an importable `schema.json` without seeing the app.

## Top level

```json
{
  "version": 2,
  "seed": "42",            // optional; string or number; same seed => identical data
  "format": "xml",         // optional; "xml" | "json" | "csv"
  "active": 0,             // optional; index of the entity tab to open
  "entities": [ ... ]      // required; one entry per record type, ORDER MATTERS
}
```

Entities generate **in array order**. A `Reference` field may only point to an
entity that appears **earlier** in the array.

## Entity

```json
{
  "name": "Contacts",      // unique display name; Reference fields address it by this
  "rows": "100",           // base record count, 1..10000 (string or number)
  "root": "contacts",      // XML only: root element name
  "record": "contact",     // XML only: per-record element name
  "dupLevel": "off",       // "off" | "light" | "medium" | "heavy" | "targeted"
  "dupPct": "20",          // % of records that get duplicate variants (dups only)
  "dupMax": "2",           // max variants per duplicated record, 1..5 (dups only)
  "fields": [ ... ]
}
```

Duplicate variants exist to test matching/dedup engines: originals and their
variants share an auto-added `match_id` column (ground truth). `light/medium/
heavy` apply preset, field-type-aware damage; `targeted` uses per-field
similarity targets (see `sim` below).

## Field

```json
{ "name": "<field path>", "type": "<type name>", "opts": { ... } }
```

Optional, only meaningful when the entity's `dupLevel` is `"targeted"`:

```json
"sim": { "algo": "jw", "target": "0.90" }   // "jw" = Jaro-Winkler, "lev" = Levenshtein
```

A variant's value for this field is fuzzed until its similarity to the
original lands as close as possible to `target` (0.5–1.0). Fields without
`sim` are copied unchanged in targeted mode.

### Field path notation (`name`)

Structure is encoded in the field name using dotted paths:

| Syntax | Meaning | XML result |
|---|---|---|
| `address.city` | dots nest elements | `<address><city>…</city></address>` |
| `order.@id` | `@` on the LAST segment makes an XML attribute | `<order id="…">` |
| `friend[3]` | repeat exactly 3× | three `<friend>` elements |
| `item[2-5]` | repeat a random 2–5× per record | 2–5 `<item>` elements |

Rules: at most **one repeating segment per path**; sibling fields sharing the
same repeating prefix (e.g. `orders.order[1-3].sku` and
`orders.order[1-3].qty`) share one count per record so their parts line up.
In JSON output, nesting becomes objects and repeats become arrays; in CSV the
full path is the column header and repeated values join with `|`.

### Type names and their `opts`

Type names must match EXACTLY (case and spacing). Omitted opts use defaults.

| `type` | `opts` | Generates |
|---|---|---|
| `Row Number` | — | 1, 2, 3, … |
| `First Name` / `Last Name` / `Full Name` | — | person names |
| `Email` / `Phone` | — | contact fields |
| `Street Address` / `City` / `State` / `State Abbr` / `Zip Code` / `Country` | — | address parts |
| `Company` / `Job Title` | — | org fields |
| `UUID` | — | v4 UUID |
| `Boolean` | — | true/false |
| `Number` | `{"min":"1","max":"100","decimals":"0"}` | random number |
| `Date` | `{"from":"2024-01-01","to":"2026-08-27","dateFormat":"YYYY-MM-DD"}` | random date; tokens `YYYY MM DD HH mm ss` |
| `Custom List` | `{"values":"red, green, blue"}` | one value from the comma-separated list |
| `Static Value` | `{"value":"fixed"}` | the same value every record |
| `Lorem Words` | `{"count":"3"}` | placeholder words |
| `Faker (any)` | `{"method":"finance.iban"}` | any no-argument @faker-js/faker v9 method by path (e.g. `commerce.isbn`, `vehicle.vin`, `internet.username`) |
| `Reference` | `{"entity":"Accounts","field":"id","unique":""}` | a value already generated for an EARLIER entity; `"unique":"1"` uses each value at most once (one-to-one) |
| `Formula (JS)` | `{"expr":"<JavaScript expression>"}` | computed per record — see below |

### Formula (JS) expressions

`expr` is a **single JavaScript expression** (not statements) evaluated per
record after all non-formula fields, in field order (a formula may reference
an earlier formula). Environment:

- `field('name')` — another field's value (current repeat index if repeated)
- `fields('name')` — the full array for a repeated field (use the full path
  as the name, e.g. `fields('orders.order[1-3].qty')`)
- `i` — current repeat index (0-based) when the formula field itself repeats
- `row` — the whole record so far, keyed by field name
- Helpers: `normalize(s)` (lowercase, strip non-alphanumerics),
  `concat(...)`, `pad(v, len, ch?)`, `rand(min, max)` (seeded integer)
- Plus ordinary JavaScript: string methods, `Math`, ternaries, IIFEs.

Examples: `(field('first_name')+'.'+field('last_name')).toLowerCase()`,
`'CUST-' + pad(field('id'), 6)`, `rand(2000,40000)/100`.

## Mapping an XSD to this format

- Each top-level repeating element type → one **entity** (`record` = the
  element name, `root` = its container).
- Leaf `xs:element` → a field; nested complex types become dotted paths.
- `xs:attribute` → `@name` on the last path segment.
- `minOccurs`/`maxOccurs` → `[min-max]` on the repeating segment
  (`maxOccurs="unbounded"` → pick a sensible cap, e.g. `[1-5]`).
- `xs:string` → a semantically matching type (`First Name`, `City`,
  `Faker (any)`, or `Custom List` for enumerations); `xs:int`/`xs:decimal` →
  `Number`; `xs:date`/`xs:dateTime` → `Date`; `xs:boolean` → `Boolean`;
  keyref/foreign-key relationships → `Reference`.
- `xs:enumeration` values → `Custom List` with those values.

## Validation

Import the file in the app (Import schema). Malformed files are rejected with
a message; unknown type names fall back to `First Name` (so type strings must
be exact); files containing `Formula (JS)` fields load with the preview held
until the formulas are reviewed. Generated-data files (arrays of records) are
rejected — this format describes rules, not data.
