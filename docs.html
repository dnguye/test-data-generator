Overview

Test Data Generator builds realistic fake data from a schema you define: add fields, pick a type for each, press download. Output is nested XML, JSON, or flat CSV. Everything runs in your browser — no server, no account, and no data leaves the page.

Quick start

  1. Add a field (or press Load example). Each card has the field name on top and the type picker below it.
  2. Click the type and start typing to search — built-in types plus the full Faker catalog.
  3. Watch the preview update as you edit (Ctrl/⌘+Enter refreshes on demand). Each card also shows a live sample value.
  4. Pick a format, set the row count, and Download.

Drag the dotted handle to reorder fields; the copy icon duplicates a field.

Nesting, attributes & repeats

Structure lives in the field name, using three pieces of syntax:

SyntaxMeaningXML output
address.citydots nest elements<address><city>…</city></address>
order.@id@ on the last part makes an XML attribute<order id="…">
friend[3]repeat exactly 3×three <friend> elements
item[2-5]repeat a random 2–5× per record2–5 <item> elements

Shared counts: sibling fields under the same repeating segment share one count per record, so the parts of each repeated element line up. These two fields always produce the same number of orders:

orders.order[1-3].sku
orders.order[1-3].qty

In JSON that becomes:

"orders": { "order": [
  { "sku": "978-1-56619-909-4", "qty": 2 },
  { "sku": "978-0-7645-7682-9", "qty": 7 }
] }

One repeating segment per field path. In CSV, nested names become the column header and repeated values are joined with |.

Linked entities (referential integrity)

When you need separate files that join by ID — Accounts and the Contacts that point at them — add an entity tab per record type. Each tab has its own fields, row count, and (for XML) element names.

Generation order is tab order, left to right, in one run. Parents generate first, then children pick from the values the parents actually produced — so every run, and every download, is internally consistent. Use the ‹ › arrows on the active tab to reorder, and rename a tab in place.

The Reference field

On the child, give the linking field the Reference type and pick the source entity and field:

Contacts · account_id
  Reference → from: Accounts · field: id
  • Default: each child picks a random parent value — a natural many-to-one (several Contacts per Account).
  • unique: each parent value is used at most once — a one-to-one link. If the child has more rows than the parent has values, the extra rows come out as #REF and the status bar warns you before you download.

A Reference may only point at a tab to its left (parents must exist first); anything else produces #REF with an explanation in the status bar. Formulas on the child can read the reference like any other field — e.g. field('account_id') + '-' + field('id') for a compound key.

Downloading

Download saves the active tab's file; Download all saves one file per entity (accounts.csv, contacts.csv, …) from a single generation run, so the IDs line up across files. With a seed set, the entire linked dataset is reproducible.

The live preview samples parent values from each parent's first 500 rows to stay fast; downloads always generate full row counts.

Testing matching & dedup

To test a matching or deduplication engine you need records that are almost the same — a person entered twice with a typo, a different phone format, a missing value. The dups control in the toolbar does this per entity:

dups: [ off | light | medium | heavy ]   20 %   × 2

With dups on, the chosen percentage of records get 1 to ×N fuzzed duplicate variants. Rows are shuffled so duplicates are not adjacent, and a match_id column is added: an original and its variants share a value, a record with no duplicates has its own. That column is the ground truth — pairs that share a match_id should match; strip the column before feeding the file to your matcher, then score its output with a group-by.

What each level does

LevelFields fuzzedKinds of damage
light1case changes and stray whitespace only — trivially matchable
medium1–2typos (transpose / drop / double a letter), email local-part fuzz, phone reformatting, date ±1 day, a wrong digit in a zip
heavy2–3everything above, plus double typos, blanked values, transposed month/day, numbers ±1
targetedyour choiceper-field similarity thresholds — see Targeted similarity below

Damage is chosen by field type, so a phone gets reformatted rather than misspelled and a date shifts by a day rather than gaining a letter.

Targeted similarity

The presets make records messy; the targeted level makes them exactly this hard to match. Choose dups: targeted and each field card gains a similarity control:

address   [ Jaro-Winkler ≈ ]  [ 0.90 ]
name      [ exact copy in variants ]

A variant's targeted field is fuzzed until its similarity to the original lands as close as possible to the threshold under the chosen algorithm — Jaro-Winkler or Levenshtein (normalized) — while every field left at exact copy is copied unchanged. That lets you generate pairs right at your matcher's threshold: a batch at 0.92 that should match and a batch at 0.80 that shouldn't.

Similarity is quantized — each character edit moves the score in steps, and a short value like TX can't land on an arbitrary number — so the engine gets as close as it can and the status bar reports the achieved average per field (e.g. address 0.897) as the preview refreshes. In testing, targets of 0.75–0.90 on realistic names and addresses land within ±0.03 essentially always.

What stays intact

  • UUID fields regenerate on each variant — a duplicate is a distinct system record with its own ID.
  • Row Number renumbers sequentially over the final (shuffled) output.
  • Reference, Boolean and Static Value fields are copied unchanged — a duplicate Contact still points at the same Account.

The row count is the number of base records; the output file is larger by the variants. With a seed set, the entire messy dataset — including which records got duplicates and how they were fuzzed — is reproducible.

Formulas (JS)

A Formula (JS) field is a JavaScript expression evaluated per record, after all other fields — so it can read them. Formulas run in field order, so a formula can also reference an earlier formula.

NameWhat it gives you
field('name')the value of another field (at the current repeat index, if repeated)
fields('name')the full array for a repeated field
ithe current repeat index (0-based) when the formula field itself repeats
rowthe whole record so far, keyed by field name
normalize(s)lowercase, strip everything but letters and digits
concat(a, b, …)join values into one string
pad(v, len, ch?)left-pad to a length, '0' by default
rand(min, max)random integer, inclusive — uses the seed

Any plain JavaScript works too: string methods, Math, ternaries, template literals. Formulas run in your own browser on data generated in the page — still, only paste expressions you trust.

Formula recipes

Copy these into a Formula (JS) field's expression box. They assume fields named first_name, last_name, etc. — change the names to match your schema.

Combining fields

// username: lenora.kuhlman
(field('first_name') + '.' + field('last_name')).toLowerCase()

// full name with a middle initial
field('first_name') + ' ' + field('middle')[0] + '. ' + field('last_name')

// normalize: lenorakuhlman (lowercase, letters and digits only)
normalize(field('first_name') + field('last_name'))

Changing case & shape

// UPPERCASE
field('city').toUpperCase()

// lowercase
field('city').toLowerCase()

// Capitalize Each Word
field('city').replace(/(^|\s)\S/g, c => c.toUpperCase())

// slug: port-angeles
field('city').toLowerCase().trim().replace(/[^a-z0-9]+/g, '-').replace(/^-+|-+$/g, '')

// initials: LK
(field('first_name')[0] + field('last_name')[0]).toUpperCase()

// trim whitespace
field('notes').trim()

IDs & codes

// padded code: CUST-000042 (uses a Row Number field named id)
'CUST-' + pad(field('id'), 6)

// random SKU: SKU-387
'SKU-' + pad(rand(1, 999), 3)

// numbered repeats: ITEM-1, ITEM-2, … (in a repeating field)
'ITEM-' + (i + 1)

CRM-style record IDs

Every recipe below uses rand(), so a seed makes the IDs reproducible.

// Salesforce 15-char ID: 003AD8rgZcOitPJ
// key prefix picks the object: 001 Account · 003 Contact · 006 Opportunity · 00Q Lead · 500 Case
'003' + Array.from({length: 12}, () => 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789'[rand(0, 61)]).join('')

// Salesforce 18-char ID with a VALID checksum suffix: 006vgMWShS8P2LIAX0
// (the last 3 chars encode the casing of the first 15, like real SF IDs)
(() => {
  const chars = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789';
  let id = '006';                                    // 006 = Opportunity
  for (let k = 0; k < 12; k++) id += chars[rand(0, 61)];
  const map = 'ABCDEFGHIJKLMNOPQRSTUVWXYZ012345';    // real SF suffix alphabet
  let sfx = '';
  for (let c = 0; c < 3; c++) {                      // 3 chunks of 5 chars:
    let b = 0;                                       // bit per uppercase position
    for (let p = 0; p < 5; p++) if (id[c*5+p] >= 'A' && id[c*5+p] <= 'Z') b |= 1 << p;
    sfx += map[b];
  }
  return id + sfx;
})()

// HubSpot-style numeric record id: 239179627
rand(100000000, 999999999)

// Zendesk-style sequential ticket: #10001 (uses a Row Number field named id)
'#' + (10000 + field('id'))

// Jira-style issue key: CRM-3618
'CRM-' + rand(1000, 9999)

// Stripe-style prefixed token: cus_hvE4imq7m5zCKW
'cus_' + Array.from({length: 14}, () => 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789'[rand(0, 61)]).join('')

// Dynamics 365 uses GUIDs — no formula needed, use the UUID field type

Numbers & conditions

// price with 2 decimals: 214.55
rand(2000, 40000) / 100

// conditional label
field('qty') > 5 ? 'bulk' : 'single'

// sum a repeated field (use the sibling's full field name)
fields('orders.order[1-3].qty').reduce((a, b) => a + b, 0)

// weighted choice: ~80% active
rand(1, 10) <= 8 ? 'active' : 'inactive'

Seeds & reproducibility

Leave seed empty for different data on every run. Set a seed and the same schema + seed produces byte-identical output, every time, on any machine — useful for repeatable test suites. The preview shows which seed was used, so you can pin a result you like.

Schema files

Export schema saves your setup as JSON; Import schema loads it back. Keep one file per data model.

{
  "version": 2,
  "entities": [
    { "name": "Accounts", "rows": "20", "root": "accounts", "record": "account",
      "fields": [
        { "name": "id", "type": "UUID", "opts": {} },
        { "name": "name", "type": "Company", "opts": {} }
      ] },
    { "name": "Contacts", "rows": "100", "root": "contacts", "record": "contact",
      "fields": [
        { "name": "first_name", "type": "First Name", "opts": {} },
        { "name": "account_id", "type": "Reference",
          "opts": { "entity": "Accounts", "field": "id", "unique": "" } }
      ] }
  ]
}

Older single-entity schema files ({"root", "record", "fields": […]}) still import — they load as one entity.

The specification

# Schema JSON specification (v2)

This document fully specifies the import/export file format of **Test Data
Generator** (https://dnguye.github.io/Test-data-generator/). It is written so
that a person — or an AI given an XSD, sample XML, or a plain description —
can author an importable `schema.json` without seeing the app.

## Top level

```json
{
  "version": 2,
  "seed": "42",            // optional; string or number; same seed => identical data
  "format": "xml",         // optional; "xml" | "json" | "csv"
  "active": 0,             // optional; index of the entity tab to open
  "entities": [ ... ]      // required; one entry per record type, ORDER MATTERS
}
```

Entities generate **in array order**. A `Reference` field may only point to an
entity that appears **earlier** in the array.

## Entity

```json
{
  "name": "Contacts",      // unique display name; Reference fields address it by this
  "rows": "100",           // base record count, 1..10000 (string or number)
  "root": "contacts",      // XML only: root element name
  "record": "contact",     // XML only: per-record element name
  "dupLevel": "off",       // "off" | "light" | "medium" | "heavy" | "targeted"
  "dupPct": "20",          // % of records that get duplicate variants (dups only)
  "dupMax": "2",           // max variants per duplicated record, 1..5 (dups only)
  "fields": [ ... ]
}
```

Duplicate variants exist to test matching/dedup engines: originals and their
variants share an auto-added `match_id` column (ground truth). `light/medium/
heavy` apply preset, field-type-aware damage; `targeted` uses per-field
similarity targets (see `sim` below).

## Field

```json
{ "name": "<field path>", "type": "<type name>", "opts": { ... } }
```

Optional, only meaningful when the entity's `dupLevel` is `"targeted"`:

```json
"sim": { "algo": "jw", "target": "0.90" }   // "jw" = Jaro-Winkler, "lev" = Levenshtein
```

A variant's value for this field is fuzzed until its similarity to the
original lands as close as possible to `target` (0.5–1.0). Fields without
`sim` are copied unchanged in targeted mode.

### Field path notation (`name`)

Structure is encoded in the field name using dotted paths:

| Syntax | Meaning | XML result |
|---|---|---|
| `address.city` | dots nest elements | `<address><city>…</city></address>` |
| `order.@id` | `@` on the LAST segment makes an XML attribute | `<order id="…">` |
| `friend[3]` | repeat exactly 3× | three `<friend>` elements |
| `item[2-5]` | repeat a random 2–5× per record | 2–5 `<item>` elements |

Rules: at most **one repeating segment per path**; sibling fields sharing the
same repeating prefix (e.g. `orders.order[1-3].sku` and
`orders.order[1-3].qty`) share one count per record so their parts line up.
In JSON output, nesting becomes objects and repeats become arrays; in CSV the
full path is the column header and repeated values join with `|`.

### Type names and their `opts`

Type names must match EXACTLY (case and spacing). Omitted opts use defaults.

| `type` | `opts` | Generates |
|---|---|---|
| `Row Number` | — | 1, 2, 3, … |
| `First Name` / `Last Name` / `Full Name` | — | person names |
| `Email` / `Phone` | — | contact fields |
| `Street Address` / `City` / `State` / `State Abbr` / `Zip Code` / `Country` | — | address parts |
| `Company` / `Job Title` | — | org fields |
| `UUID` | — | v4 UUID |
| `Boolean` | — | true/false |
| `Number` | `{"min":"1","max":"100","decimals":"0"}` | random number |
| `Date` | `{"from":"2024-01-01","to":"2026-08-27","dateFormat":"YYYY-MM-DD"}` | random date; tokens `YYYY MM DD HH mm ss` |
| `Custom List` | `{"values":"red, green, blue"}` | one value from the comma-separated list |
| `Static Value` | `{"value":"fixed"}` | the same value every record |
| `Lorem Words` | `{"count":"3"}` | placeholder words |
| `Faker (any)` | `{"method":"finance.iban"}` | any no-argument @faker-js/faker v9 method by path (e.g. `commerce.isbn`, `vehicle.vin`, `internet.username`) |
| `Reference` | `{"entity":"Accounts","field":"id","unique":""}` | a value already generated for an EARLIER entity; `"unique":"1"` uses each value at most once (one-to-one) |
| `Formula (JS)` | `{"expr":"<JavaScript expression>"}` | computed per record — see below |

### Formula (JS) expressions

`expr` is a **single JavaScript expression** (not statements) evaluated per
record after all non-formula fields, in field order (a formula may reference
an earlier formula). Environment:

- `field('name')` — another field's value (current repeat index if repeated)
- `fields('name')` — the full array for a repeated field (use the full path
  as the name, e.g. `fields('orders.order[1-3].qty')`)
- `i` — current repeat index (0-based) when the formula field itself repeats
- `row` — the whole record so far, keyed by field name
- Helpers: `normalize(s)` (lowercase, strip non-alphanumerics),
  `concat(...)`, `pad(v, len, ch?)`, `rand(min, max)` (seeded integer)
- Plus ordinary JavaScript: string methods, `Math`, ternaries, IIFEs.

Examples: `(field('first_name')+'.'+field('last_name')).toLowerCase()`,
`'CUST-' + pad(field('id'), 6)`, `rand(2000,40000)/100`.

## Mapping an XSD to this format

- Each top-level repeating element type → one **entity** (`record` = the
  element name, `root` = its container).
- Leaf `xs:element` → a field; nested complex types become dotted paths.
- `xs:attribute` → `@name` on the last path segment.
- `minOccurs`/`maxOccurs` → `[min-max]` on the repeating segment
  (`maxOccurs="unbounded"` → pick a sensible cap, e.g. `[1-5]`).
- `xs:string` → a semantically matching type (`First Name`, `City`,
  `Faker (any)`, or `Custom List` for enumerations); `xs:int`/`xs:decimal` →
  `Number`; `xs:date`/`xs:dateTime` → `Date`; `xs:boolean` → `Boolean`;
  keyref/foreign-key relationships → `Reference`.
- `xs:enumeration` values → `Custom List` with those values.

## Validation

Import the file in the app (Import schema). Malformed files are rejected with
a message; unknown type names fall back to `First Name` (so type strings must
be exact); files containing `Formula (JS)` fields load with the preview held
until the formulas are reviewed. Generated-data files (arrays of records) are
rejected — this format describes rules, not data.
